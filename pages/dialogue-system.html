Behind the Text Box: Flexible Dialogue System in “A Search For a Shiny Thing”

Introduction

In 2024, I co-founded a tiny indie studio called The Notlanders and for the next two years I worked on a photography adventure game titled “A Search for a Shiny Thing”. Although the project is currently on indefinite hiatus, it's development presented many interesting challenges which required creative solutions. In this article, I will walk you through the dialogue system I developed for the game and talk about the things that worked and the things that didn't.

The Problem

For “A Search For a Shiny Thing” we endeavored to create a tiny but dense world full of things to explore. The game places a large emphasis on narrative, exploration and puzzle solving. The game features many colorful characters the protagonist meets along the way. Discovering the people on the island was just as important as discovering locations. It wasn't enough for NPCs to simply parrot a few lines of dialogue, we wanted branching conversations with choices that may or may not be available depending on what quests the player has completed and whether they discovered something in the world. Out of the box Unity doesn't have a dialogue system. There are tools that can be bought on the asset store, but we wanted to make our custom tools both as a learning experience and for control.

Authoring and Import

The dialogues are authored in a simple spreadsheet. The dialogues are laid out line by line in a spreadsheet. All lines must have a key, lines with the same key are grouped together into one dialogue. The line can optionally have an actor, topic and text. The key and actor fields are invisible to the player and only serve to identify the dialogue and optionally who is speaking it, while topic and text are language specific. A line with no actor, topic and text is still technically valid, though we expect a line to have at least a topic or text. That is because lines can be used in multiple different contexts. For example, we use the same system for interacting with objects as we do for speaking with NPCs. For grabbing a hammer from a toolbox we have a line with a key "TOOL_BOX_HAMMER" and it contains only a topic. We display the topic selection box to the player when they interact with the toolbox, and it has the option "Grab the hammer" (localized to whatever language the player is playing in).

The spreadsheet is exported as a .tsv file. It could've been .csv but .tsv was slightly easier to parse considering there are plenty of commas in the text. Currently, we don't validate the spreadsheet, but ideally we need to ensure that it contains no tabs before being exported. Then you manually import the spreadsheet into Unity. The project was not built with addressables, so the spreadsheets are placed into the streaming assets folder instead. A custom asset post-processing parses the spreadsheet and creates a scriptable object for each dialogue key. These scriptable objects act as searchable keys when you're setting up a dialogue graph and allow you to preview dialogue and set up inline actions, such as changing the NPCs facial expression. I'll talk about both dialogue graphs and actions later. Each of those scriptable objects keeps a reference to the spreadsheet it's associated with.

Graph Tool

The next step in the process is to create a dialogue graph. To accommodate for conditional / branching dialogues I created a node-based tool, taking a little bit of inspiration from behavior trees and assembly language. The project uses Unity 2022, and it was unfortunately not feasible to update it to Unity 6 because there was a high probability all of our custom rendering stuff would break, perhaps without a possibility of repair, because the scriptable render pipeline API changed. Because of that I was unable to use the graph toolkit that is available in Unity 6. To save time, I decided to use a third-party plugin called xNode which is a framework for developing node-based tools just like the graph toolkit. xNode is no longer maintained and isn't quite meant to be used in the way I'm using it, but it did its job.

Here are all the nodes available in the dialogue graph:

  • Dialogue
  • Action
  • Condition
  • Branch (Flow)
  • Choice (Flow)
  • Selector (Flow)
  • Jump (Flow)
  • Label (Flow)
  • And (Logic)
  • Not (Logic)
  • Or (Logic)
  • Xor (Logic)

The most central node is of course the "Dialogue" node. It has a field for referencing the dialogue scriptable object, a pin for specifying a condition that decides whether the dialogue is valid/able to play and pins connecting to the previous node and the next node. A branch will take either the true or false path based on the evaluated condition. A choice brings up a topic selection menu to the player where the can choose which dialogue option they want to choose. A selector, similar to a behavior tree, will evaluate all of it's "children" nodes from top to bottom and play the first available one. Jump and label allow moving between different parts of the graph and creating cyclical dialogues. And/Not/Or/Xor are logical nodes that allow combining multiple conditions in various ways.

Actions and Conditions

Conditions evaluate the current game state and return true when the requirements are satisfied, or false otherwise. The base Condition class defines the common interface and individual condition types then implement their own logic. For example, an inventory item condition checks whether a character (usually player) has a specific item in their inventory. You specify what character's inventory to check by referencing an ID scriptable object, the item scriptable object and optionally quantity.

[Serializable]
public abstract class Condition
{
    public abstract bool Check();
}
Click to view: Inventory Item Condition 
[AddTypeMenu("Item/Inventory Item")]
[Serializable]
public class InventoryItemCondition : Condition
{
    [SerializeField] private ScriptableID id;
    [SerializeField] private Item item;
    [SerializeField] private int quantity;

    public override bool Check()
    {
        if (Locator.GetByID<Inventory>(id, out var inventory))
        {
            Debug.Assert(item != null);
            return inventory.HasQuantity(item, Mathf.Max(1, quantity));
        }

        return false;
    }
}

In the context of a dialogue graph we use conditions to determine which of the selector's child node should be played, to hide dialogues from the player until they fulfill a requirement and to control whether an action should be triggered.

At Runtime / Text Box

When the scene loads and the scriptable object is loaded into memory, it registers itself with the text manager. After the scene is fully loaded, the text manager deserializes all the dialogue from the relevant spreadsheet into the scriptable object taking into account the current language setting. This process happens for all other text in the game as well, so the player can change the language of the game at any time and the game simply has to call this ReloadText function.

Last but not least, how is the text displayed to the player? Instead of going for visual novel style text boxes, we went with "thought clouds" that appear above NPCs. But how do we position the thought clouds? We planned for some NPCs to move freely in the world and that meant manually setting up dialogue cameras was not an option. That meant we needed either to implment a smart camera system that would check for any visual obstructions, or we could keep the current gameplay camera and simply make sure the text boxes are positioned correctly. We went with the latter option. We took inspiration from A Short Hike. The thought clouds appear above the speaking NPCs without obstructing neither the speaker nor the player. The text box's desired position is to always be directly above the speaker. I apply a correction on the x-axis if the current desired position leads to an overlap with the non-speaker actor. I clamp the position of the box to never go outsite the screen. This simple setup supports dialogues with 2 actors, but considering that I'm working with AABBs it wouldn't be too difficult to implement solver that can handle several actors.

Topic selection will appear at the bottom whenever the dialogue graph hits a choice node. Choices that don't meet conditions will either not appear or will appear as questions marks if we want to hint the NPC has an undiscovered topic.
